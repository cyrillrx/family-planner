# ADR-003: Firestore for synchronization, with an owned service for privileged work

> **Status**: Accepted | **Date**: 2026-09-02 | **Context**: [PRD-001](../prd/prd-001-group-and-synchronization.md) is agreed; no V1 feature can start until the stack that upholds it is chosen.

## Decision

The architecture is **hybrid**, in two parts that do not overlap:

| Part                             | Responsibility                                                                                                               |
|----------------------------------|------------------------------------------------------------------------------------------------------------------------------|
| **Cloud Firestore**              | Shared state, real-time propagation between members, the local offline cache, and reconciliation on reconnect                |
| **An owned service** (`server/`) | Invitation redemption, scheduled notification delivery, any outbound call that carries a secret, and custody of every secret |

**Local persistence** is Firestore's own offline cache. No second local database is introduced for shared data. SQLDelight is not adopted by this ADR.

**Identity** is Firebase Auth anonymous sign-in. The member identifier of PRD-001 Phase 1 is **generated by us and stored on the member's record, with the Firebase UID held beside it as the credential that authenticates it.** The two are deliberately not the same value: see "Keeping the exit open" below.

**Identifiers are ours.** Every shared record carries an identifier the client generates — a UUID — rather than one the store assigns. Firestore document paths are addressing, not identity.

**Conflict resolution** is last-write-wins on server timestamps, as the store performs it natively. A deletion that lands last wins. This reverses a PRD-001 requirement; the PRD is revised to v0.3 in the same change.

**The invitation** is the only privileged operation. Its shape:

- A member creates an invitation; the code is 128 bits of randomness, delivered as a share link or QR rather than typed.
- Redemption goes through the owned service, which validates and writes the membership in one transaction. Two people cannot consume the same code.
- Security rules deny every client write to the group's member list. Without that denial the service is a formality.
- The invitation is single-use, expiring and revocable, enforced by the service and not by the interface.
- The group identifier is not guessable, and reads are scoped by membership rather than by knowledge of the identifier.
- The code is never written to any log, analytics event or crash report.

The component that holds it is **`server/`**, replacing the `telegram-bot/` slot in the repository structure. Notifications become one of its jobs rather than its identity: a component holding every secret, the outbound calls that carry them and the only privileged write in the product is not "the Telegram bot", and `AGENTS.md` makes the component name the commit scope — a membership write committed as `feat(telegram-bot)` would mislead anyone reading the log. Nothing is moved by the rename, `telegram-bot/` having never been created.

## Context

PRD-001 fixes the behaviour: reads served from local storage, the app fully usable offline, durability before the interface confirms, propagation between members in seconds, deterministic convergence, group isolation enforced on read, and conflict behaviour testable in `shared/core` without a network. [ADR-002](adr-002-desktop-product-surface.md) adds that every client dependency must exist on JVM. The server-side component has to be able to read the group's data from a script.

One constraint was not in the PRD and reframes the question. The product has to reach services that authenticate with a secret — notification delivery and AI meal generation are both on the roadmap — and a secret cannot live in a distributed client, because whatever ships can be extracted. It also needs somewhere trusted to perform the one write the client is not allowed to make. Which providers those turn out to be is not settled, and is not decided here; that they need a caller the client cannot impersonate is. **A service of our own is required whatever else is chosen.**

The question is therefore not "a backend service or a BaaS". It is: given that a service will exist anyway, how much of the synchronization does it also carry? The candidates are points on that axis, not camps.

## Rationale

### Why the split falls where it does

Real-time push and offline reconciliation are the expensive, subtle parts — reconnection, resume after a long absence, ordering, convergence. Request/response work is not: validating a code, proxying an API call, sending a message. The line is drawn along that difficulty, so the hard half is delegated and the easy half stays where the secrets already have to be.

The arrangement also fails well. If the owned service is down, synchronization keeps working and the app is unaffected; only the notifications and the features needing an outbound call stop. The product's core value does not depend on our uptime. The reverse split — owning the sync and delegating nothing — would put a daily-use family app behind our own availability.

### Why Firestore

**Offline-first is the requirement that costs the most, and Firestore is the only candidate that satisfies it without us writing a sync engine.** Its local cache serves reads, accepts writes offline, and reconciles on reconnect. Supabase has no offline layer; choosing it means writing that engine, which is the work of the full-custom option with less control over it.

**It answers PRD-001's hardest open question.** The PRD asks how authentication will later attach an existing anonymous member to an account without losing their data. Firebase Auth's anonymous sign-in links to a permanent credential while keeping the same UID — the migration path exists as a first-class operation instead of being something to invent in Phase 2.

**Its free tier does not pause.** Supabase suspends a free project after a week without use, and PowerSync deactivates one after a week of inactivity. A family that goes quiet for a fortnight would come back to an application that is down until someone opens a dashboard. Firebase's Spark plan has no equivalent behaviour, and its ceilings — 1 GiB stored, 50K reads and 20K writes a day, 50K monthly active users, 2M function invocations — are far above what a handful of people generate.

**Reconciliation after a long absence is handled by the SDK.** PRD-001 requires explicit deletions to be retained seven days so a returning device does not miss them. Firestore manages resumption itself and falls back to a full re-query when a client has been away too long, so the retention requirement is met by the store rather than by tombstones we would design, write and test.

**Script access does not constrain the server's language.** The `firebase-admin` SDK exists for Python and for the JVM, so this choice leaves `server/` free to be either — which matters, because that question is still open below.

### Why not the alternatives

**Supabase** wins on JVM support, which is first-class rather than an alpha port, and on Postgres being a better fit than a document store for recipes and ingredients. It loses on the requirement that matters most: no offline layer, so the whole sync engine becomes ours. Its free-tier suspension is a second strike for a product used daily by non-technical people.

**PowerSync** is the closest challenger. It exists precisely to make local SQLite an offline-first mirror of Postgres, its writes already route through an endpoint of ours — which is exactly where invitation enforcement belongs — and its Open Edition can be self-hosted. It loses on parts count: PowerSync plus a Postgres plus our service is three things to operate against Firestore plus our service, and its free tier both deactivates on inactivity and caps concurrent clients at 50. It is the option to revisit first if Firestore's data model becomes the constraint.

**A full custom backend** has one genuine advantage no BaaS can match: `shared/core` already targets JVM for coverage reasons, so a Ktor server could depend on the same domain module as the client, with one definition of the model on both sides. It loses because the expensive work — real-time push, offline reconciliation, and authentication in Phase 2 — is exactly the part it makes ours, and that work is not the product. The features are.

### Keeping the exit open

Two different moves get confused under "changing the database later", and they do not cost the same.

**Swapping one sync provider for another** — Firestore for PowerSync, say — is bounded. Both supply the local mirror, the offline write queue and the resumption logic, so what changes is the implementation behind the interface in `shared/core`. That is a real swap.

**Hosting the synchronization ourselves is not a swap.** This ADR leans on Firestore for four things that would then have to be written: the offline cache *is* the local persistence, durability before confirmation is upheld by the SDK, propagation in seconds comes from its listeners, and resumption after a long absence is handled by the store rather than by tombstones we design. Leaving for our own engine means building the expensive half that this decision exists to delegate. The honest cheapest route to self-hosted sync is **PowerSync's Open Edition on our own infrastructure**, which keeps the offline-first contract — not writing a sync engine.

The interface in `shared/core` therefore protects the **call sites**, not the **behaviour**. It is necessary and it is not sufficient, and pretending otherwise would make a future decision look cheaper than it is.

What does buy real optionality, at no cost today:

- **Our own member identifier, with the Firebase UID beside it.** This is the one thing that cannot be migrated afterwards. Phase 1 identities are anonymous, device-local and unrecoverable, so they cannot be re-authenticated somewhere else; if the member identifier *were* the UID, leaving Firebase before authentication exists would destroy every member's identity, and with it their group membership and the attribution of their records. Two fields instead of one, decided now, is the difference between a possible migration and an impossible one.
- **Client-generated record identifiers.** Otherwise the identifier space belongs to the vendor and every cross-reference has to be rewritten on the way out.
- **Authorization expressed as rules, not as logic.** Security rules should scope reads and deny writes. Anything resembling a decision belongs in `shared/core` or in `server/`, where it survives the store it was written against.

### Why no second local database

With Firestore's cache serving reads, a second store for shared data would need its own write path, its own conflict handling and its own tests, for no behaviour the PRD asks for. SQLDelight was a draft-spec assumption for the recipe library, and whether that library is even shared is an open question below.

## Consequences

- **Vendor concentration on Google.** Firestore, Auth and Functions come from one provider, and PRD-001's guarantees are then partly upheld by a proprietary SDK. This is the cost of the decision, and the interface in `shared/core` only partly offsets it: moving to another offline-first provider is bounded work, while moving to a synchronization engine of our own means writing the expensive half this ADR delegates. See "Keeping the exit open".
- **The identity binding is the only irreversible part, and it is deliberately loosened.** A member identifier of our own, with the Firebase UID beside it, costs one extra field now. Conflating them would make leaving Firebase before Phase 2 destroy every member's identity, since anonymous Phase 1 identities cannot be re-authenticated elsewhere.
- **The JVM dependency is alpha.** `firebase-java-sdk` 0.6.2 is described by its authors as alpha, and it is what makes `firebase-kotlin-sdk` run on Desktop. ADR-002 accepts this and ranks Desktop second precisely so that breakage there is survivable. Desktop is where it will surface first.
- **Whether anonymous-account linking works on the JVM port is unverified.** The port's authentication support is documented as a subset. Linking is a Phase 2 concern and mobile-first, but the assumption must be tested before Phase 2 relies on it — not after.
- **Sync must sit behind an interface in `shared/core`, with a fake implementation.** This is not optional: PRD-001 requires conflict and offline behaviour to be verifiable without a network, and Kover only measures `jvmTest`. The consequence is that no Firestore type may appear in a `shared/core` signature.
- **The owned service holds administrative credentials and therefore bypasses security rules.** Every guarantee the rules provide is void inside it. Its privileged surface must stay as small as the invitation, the proxy and the notifications, and be reviewed as the one place where a bug is unguarded.
- **The document model constrains the shared data.** Firestore is not relational; anything needing joins across the group's data will be denormalised. Recipes and ingredients are the likely pressure point, and the trigger for revisiting PowerSync.
- **The `telegram-bot/` slot becomes `server/`**, in the repository structure tables of `AGENTS.md` and the `README.md` and in the commit-scope table. One component, one deployable, one CI workflow — proportionate to a personal project, where two services to operate would not be.
- **PRD-001 is revised to v0.3** in the same change: last-write-wins replaces edit-over-delete, and the resurrection window it implied is removed. The seven-day retention stays, now satisfied by the SDK rather than by us.

## Alternatives considered

**Supabase with a hand-written offline layer** — Rejected: it makes the most expensive requirement ours while giving up the control that would justify doing so, and its free tier suspends after a week of inactivity.

**PowerSync over Postgres** — Rejected for now: three components to operate instead of two, a free tier that deactivates on inactivity and caps clients at 50. It stays the named exit: the strongest candidate if the document model becomes the binding constraint, and — in its self-hosted Open Edition — the cheapest route to owning the synchronization outright.

**A full custom backend, Ktor and Postgres** — Rejected: it takes ownership of real-time push, offline reconciliation and Phase 2 authentication, which is the costly work and none of it is the product. Its unique advantage — sharing `shared/core` between client and server — does not outweigh that.

**Firestore with SQLDelight alongside it** — Rejected: two local stores for shared data, two write paths and two sets of tests, for nothing PRD-001 asks for.

**Owning the sync and delegating only notifications** — Rejected: it puts a daily-use family application behind our own availability, and inverts the split so that the difficult half is ours.

## Open Questions

- **Is the recipe library shared across the group, or personal to a member?** PRD-001's shared list names the week plan, the grocery list, the events and the tasks — recipes are absent, which looks like an oversight rather than a decision. The answer settles whether any local database other than Firestore's cache is needed, and belongs to the meal PRD.
- **Where does `server/` run?** It has to be reachable on a schedule for the notifications and on demand for redemption — two different availability needs in one component. The draft spec offers Claude Code Routines with a Raspberry Pi as fallback; neither is decided.
- **What language is `server/` written in?** The draft spec assumes Python. Kotlin with Ktor would let it depend on `shared/core`, which already targets JVM, giving one definition of the domain model on both sides of the wire — the single advantage the full-custom backend had, and it survives in this shape. Weighed against Python being the shorter path for scripting and for the `firebase-admin` calls.
- **Does anonymous-account linking work through the JVM port?** To be tested before Phase 2 depends on it.
- **What is the retention and backup story for the group's data?** Firestore's free tier includes no scheduled export, and the PRD's durability guarantee stops at the device.
